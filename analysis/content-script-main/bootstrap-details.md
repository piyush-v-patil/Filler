# Bootstrap and message flow — contentScriptMain.js 3.1.10

This is a bounded ordinary static source inspection, not REA Evidence or observed runtime execution. Line numbers below refer to [the readable bundle](contentScriptMain.readable.js), the parent's whitespace-formatted copy whose AST was verified against the original. The current pass did not inspect the implementations in background.js or pageScript.js.

## Startup and rendering

- The bundle executes an outer IIFE (`var contentscriptmain=function(){...}();`, line 1). Its meaningful startup occurs before the framework-generated trailing `main()` wrapper, which is empty at lines 162310–162313.
- At line 162283 it registers a `m.runtime.onMessage` listener. `action: "run"` resets the previous URL/render retry delay and calls `Hhe`; `action: "triggerFill"` reads the shared store's `fill`, `fillStatus`, and `settings`, avoids starting another fill while status is `"filling"`, and otherwise calls `fill({keyPaths:null,showProgress:true,continuous:settings?.defaultContinuous??true})`. It then calls `Hhe()` immediately at line 162305.
- `Hhe` starts at line 162025. It obtains config through `Cu`, requires config.render and a browser DOM, checks `render.urlsExcluded`, and checks dimensions for non-top frames. It can exempt matching ATS URLs from the minimum frame dimensions. These are source conditions, not proof of actual matching on a particular site.
- The render path executes configured `render.initialize` actions (line 162110), including `click` and a `waitForReact` page-message handshake, then creates a React root and renders `jhe` → `Ahe` (around lines 162190–162212). `Ahe` either shows the privacy agreement or renders the state/controller tree `V$` and UI tree `xhe` (lines 161478 and 161539–161574).
- If rendering is not ready, the code retries with a delay starting at 300 ms and capped at 5 seconds, and installs a subtree/child-list MutationObserver (lines 162003–162012 and 162235–162277). A specific missing-config timer is bounded to five minutes. The error boundary has 1 s, 5 s, and 30 s recovery delays (line 161578).

## Configuration, settings, profile, and frame state

- `Cu` (line 14329) coalesces callers through `Su`. It sends `{method:"fetchRemoteConfigValues"}` to the extension runtime (line 14335), with a two-second race. It next tries cached session data via `Yc` (line 14368). If the result lacks `render`, `ATS`, `Boards`, or `ResumeScores`, it calls `uu` (line 14386). `uu` loads the packaged `remoteConfig.json` using `fetch(m.runtime.getURL(...))` (line 13983), including handling for `__atsShards` / serialized config chunks. Board-specific `findJobData` / `getJobUrl` functions are attached from bundled code (lines 14388–14396).
- `gv` (line 40801), mounted by `yv`, owns remoteConfigValues and refresh function, gets a tab ID with `{method:"getTabId"}` when tabEnabled becomes true (line 40860), and obtains automation-session status with `{method:"isAutomationSession"}` (line 40599). `yv` copies these results into shared store `f` (line 40922).
- `mv` requests `{method:"getTabFrames"}` at line 40712 and subscribes to `frameUrls`. The `fv` connection helper opens `runtime.connect({name:"sabre-state:v1"})` (line 40625), sends `{type:"subscribe",slices:...}` (line 40648), handles `snapshot` and `update`, and reconnects with exponential backoff from 250 ms up to 4 s (lines 40609–40657).
- Settings are initialized from defaults `y_` (line 64156), including `defaultContinuous:true`, then loaded/persisted by `eu` under key `["settings"]` with no expiration (lines 64171–64187). `b_` publishes settings, setSettings, and settingsReady to store `f` (line 64197). `eu` reads through `Yc` (line 13529), writes through `Kc` (line 13562), and listens for local-storage change events; `Yc` sends `{method:"getSessionItem",keys:...}` (line 13439).
- `E_` persists linkedCandidate under `uo("linkedCandidate")` and sends `{method:"getLinkedCandidate",forceRefresh:...}` (lines 64526–64576). Updates use `{method:"updateCandidate",candidateUpdate:...}` (line 64595). The controller triggers retrieval when tabEnabled is true and candidate status is absent (lines 65311–65330). It can refresh after returning from a hidden tab (lines 65332–65362).
- `normalizedProfile` is derived by `XT` from linkedCandidate, settings, resume data, cover letter, application email, and other inputs (line 65283), then published to the shared store by the `I_` controller (lines 65422 and 65459–65492). This pass did not exhaustively trace every normalization field.
- `V$` mounts `yv`, `b_`, `FN`, `e_`, `I_`, `uv`, `m_`, `uN`, `aE`, and `U$` at lines 80068–80122. This supports an architecture of React controller components publishing slices into the shared store, with the UI consuming that store.

## Page-world and extension-runtime boundaries

- The page-script loader `$$` (line 79905) adds a script element with ID `simplify-jobs-page-script` whose src is `m.runtime.getURL("pageScript.js")`. `U$` sets tabEnabled from detected support/UI conditions and invokes this loader when enabled (lines 79924–79945). Therefore pageScript.js is a separate execution-context bridge; its behavior is not fully contained in this bundle.
- One bridge operation, `lx` (line 42321), sends `__simplify__fillInput` through `window.postMessage(...,"*")` (lines 42355–42366) and waits for a same-window `__simplify__updateFilledInput` message with the matching keyPath (line 42342). This establishes a protocol and waiting logic, not proof that a particular response or fill happened.
- The application registers a runtime `getReportFrameState` handler at lines 80040–80063. It serializes the current store excluding remoteConfigValues, adds sessionId, and optionally includes rrweb events.
- A separate page bridge is registered only when `window.location.origin === "https://simplify.jobs"` (line 161977). It accepts same-window messages with `sender:"dunder"` and a suid, dispatches the method table `Ihe`, and replies with `sender:"sabre"` to the fixed simplify.jobs origin (Nhe at line 161655). Methods in this table forward operations such as applyToJob, get/set session items, importProfile, resumeId, and version to runtime handlers. Their background/API implementation is outside this pass.
- An automation-status message bridge is initialized by `V$` at line 79983. `L_` first checks navigator.webdriver or the background's isAutomationSession result (lines 65516–65530), then handles a ping and a getFillStatus request (lines 65537–65580). This is a separate protocol from the regular extension runtime listener.
- The bundled Village integration's `Ly` initialization runs on matching Simplify/Village/localhost URLs at lines 162306–162308; `Ry` can also initialize it after checking stored privacy consent (lines 25778–25795). This pass did not audit that integration's full message surface.

## Boundaries of these conclusions

The exact original minified identifiers are retained. The readable lines describe source behavior, not runtime traces or a security audit. Static checks of source/origin/message tags are not a claim of complete authorization enforcement. Backend profile retrieval, background state management, and pageScript.js execution require their own source or runtime evidence. Cross-chunk REA relationships remain subject to the parent's extraction limitations; the findings here were checked against the unchanged whole-source readable copy.
